# ☸️ 🚀 Day 51: Kubernetes Manifests and Your First Pods

### The Anatomy of a Kubernetes Manifest
Every Kubernetes resource requires a YAML manifest containing these four critical top-level fields to define its state:
* **`apiVersion`**: Specifies the API group and version to use for creating the object. For Pods, this is `v1`.
* **`kind`**: Defines the type of Kubernetes resource you want to create (e.g., `Pod`, `Deployment`, `Service`).
* **`metadata`**: Contains data that uniquely identifies the object, including its `name`, `namespace`, and organizational `labels`.
* **`spec`**: The core of the manifest where you declare the desired state of the resource, such as which container images to pull, ports to expose, and commands to run.

### Task 1: Create Your First Pod (Nginx)
**Manifest: `nginx-pod.yaml`**
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx-pod
  labels:
    app: nginx
spec:
  containers:
  - name: nginx
    image: nginx:latest
    ports:
    - containerPort: 80

```

**Execution & Verification:**

* Applied via `kubectl apply -f nginx-pod.yaml`.
* Verified internal network connectivity by running `kubectl exec -it nginx-pod -- /bin/bash` and curling `localhost:80` to successfully receive the Nginx welcome HTML.

### Task 2: Create a Custom Pod (BusyBox)

**Manifest: `busybox-pod.yaml**`

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: busybox-pod
  labels:
    app: busybox
    environment: dev
spec:
  containers:
  - name: busybox
    image: busybox:latest
    command: ["sh", "-c", "echo Hello from BusyBox && sleep 3600"]

```

**Execution & Verification:**

* Applied via `kubectl apply -f busybox-pod.yaml`.
* Because BusyBox is a lightweight utility container and not a persistent web server, the `command` overrides the default entrypoint to force it to sleep. Without this, it would exit successfully and trigger a `CrashLoopBackOff`.
* Verified the startup message using `kubectl logs busybox-pod`.

### Task 3: Imperative vs Declarative**

**1. Create a pod imperatively without a YAML file:**

```bash
kubectl run redis-pod --image=redis:latest
kubectl get pods

```

**2. Extract the live YAML generated by Kubernetes:**

```bash
kubectl get pod redis-pod -o yaml

```

*Comparison Observation:* When comparing this output to the hand-written `nginx-pod.yaml`, the generated YAML contains extensive system-injected data. Kubernetes automatically appends a `status` block (tracking IPs and container states) and populates the `metadata` with system identifiers like `uid`, `resourceVersion`, and `creationTimestamp`.

**3. Generate YAML using dry-run (without creating the pod):**

```bash
kubectl run test-pod --image=nginx --dry-run=client -o yaml

```

<img width="2488" height="734" alt="image" src="https://github.com/user-attachments/assets/e777657f-57e2-4670-bb51-933d92cb9286" />



*Comparison Observation:* 

* Saving this dry-run output produces a clean, foundational manifest. The fields (`apiVersion`, `kind`, `metadata`, `spec`) are identical in structure to the hand-written `nginx-pod.yaml`, but it strips out the live cluster `status` data, making it the perfect shortcut for scaffolding new YAML files.

### Task 4: Validate Before Applying

**1. Perform a client-side validation:**
Checks if the local YAML syntax is correct without sending it to the cluster to be created.

```bash
kubectl apply -f nginx-pod.yaml --dry-run=client

```
Note: Client-side validation only checks for valid YAML syntax and basic structure. If the YAML is well-formed, it may pass even if a required Kubernetes field is missing.

**2. Perform a server-side validation:**
Submits the manifest to the API server to validate it against the cluster's exact API schema and policies, but stops just short of actually provisioning the resource.

```bash
kubectl apply -f nginx-pod.yaml --dry-run=server

```

Note: Server-side validation strictly enforces the Kubernetes API schema. The API server immediately rejected the manifest because it detected that the container at index [0] was missing the mandatory container image, preventing a broken deployment from being scheduled.

**3. Test intentional failure:**
*Action performed:* Removed the `image: nginx:latest` line from `nginx-pod.yaml` and executed the dry-run command again.
*Error Output Received:*

```text
The Pod "nginx-pod" is invalid: spec.containers[0].image: Required value
```

### Task 5: Pod Labels and Filtering

Labels are critical for organizing resources and allowing Services/Deployments to select the correct pods.

**Label Operations Practiced:**

```bash
# View all pods and their attached labels
kubectl get pods --show-labels

# Filter pods dynamically by their specific labels
kubectl get pods -l app=nginx
kubectl get pods -l environment=dev

# Imperatively add a new label to a running pod
kubectl label pod nginx-pod environment=production

# Imperatively remove a label (notice the minus sign at the end)
kubectl label pod nginx-pod environment-

```

**What happens when you delete a standalone Pod?**
It is permanently destroyed. Because these Pods were created directly (naked Pods) rather than being managed by a higher-level controller like a `Deployment`, there is no reconciliation loop watching them. Once the API server deletes the object and the `kubelet` terminates the container, it ceases to exist. This demonstrates exactly why bare Pods are never used for production workloads.

### Hints & Best Practices

* `kubectl apply -f` creates or updates a resource from a file declaratively.
* `kubectl get pods -o wide` expands the output to show the scheduled node and internal IP address.
* `kubectl describe pod <name>` outputs the event log and state history, making it the most useful command for debugging failures.
* `kubectl logs <name>` streams the container's standard output (stdout/stderr).
* `kubectl exec -it <name> -- /bin/sh` gives you an interactive shell inside the container (use `/bin/sh` if `/bin/bash` is not available in Alpine-based images).
* **Labels** are strictly key-value pairs—they have no operational meaning to Kubernetes itself, only to selectors (Services, Deployments) that use them to target resources.
* `--dry-run=client -o yaml` is the fastest way to scaffold complex manifest templates without writing them from scratch.
