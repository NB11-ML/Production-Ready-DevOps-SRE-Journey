## 📂 Task 1: The Problem with Manual Deployments

*   **What can go wrong:** When 5 developers push code manually to the same server, version conflicts, overwritten code, and mismatched dependencies become inevitable. The production environment drifts from local environments, leading to unpredictable downtime and broken features.
*   **"It works on my machine":** This phrase means the code executes perfectly on the developer's local laptop but fails in production. It is a critical problem because local machines have different OS versions, installed packages, and environment variables than the production server.
*   **Safe deployment frequency:** Relying strictly on manual, human-driven deployments limits a team to deploying safely perhaps 1-2 times a week (or even less for monoliths). The risk of human error in typing commands or missing a step scales with every deployment.

## 📂 Task 2: CI vs. CD (Delivery) vs. CD (Deployment)

*   **Continuous Integration (CI):** The automated process of frequently merging developer code into a central repository. It runs automatically on every commit or pull request to catch syntax errors, run unit tests, and build the application. 
    *   *Example:* A GitHub Action runs `pytest` every time a developer opens a PR, blocking the merge if a test fails.
*   **Continuous Delivery (CD):** The automation of releasing validated code to a repository or staging environment, ensuring it is *always ready* to be deployed to production. The final push to production still requires a manual click (human approval).
    *   *Example:* A pipeline builds a Docker image and pushes it to Docker Hub, waiting for the QA lead to click "Deploy to Production."
*   **Continuous Deployment (CD):** The complete automation of the entire release pipeline. If the code passes all CI tests and staging checks, it is pushed directly to the live production environment with zero human intervention.
    *   *Example:* Netflix or Amazon engineers pushing a code change that automatically goes live to customers 15 minutes later after passing all automated health checks.

## 📂 Task 3: Pipeline Anatomy

*   **Trigger:** The specific event that initiates the pipeline (e.g., a `git push`, a scheduled CRON timer, or opening a Pull Request).
*   **Stage:** A logical grouping of jobs representing a phase in the lifecycle (e.g., `Build`, `Test`, `Deploy`).
*   **Job:** A distinct unit of work executed on a specific environment. Jobs in the same stage can often run in parallel.
*   **Step:** A single, sequential command or action executed within a job (e.g., running `npm install` or executing a bash script).
*   **Runner:** The actual server or virtual machine (e.g., an `ubuntu-latest` VM) that executes the steps defined in the pipeline.
*   **Artifact:** The tangible output generated by a job (e.g., a compiled binary, a `.zip` file, or a Docker image) that can be passed to the next stage or downloaded.

## 🔬 Task 5: Explore in the Wild (FastAPI)

I analyzed the popular open-source Python framework, **FastAPI** (`fastapi/fastapi`).

* **Repository & File:** `.github/workflows/test.yml`
* **What triggers it:** The workflow uses the `on` command to trigger automatically upon a `push` to the `master` branch or when a `pull_request` is opened.
* **Jobs & Runner:** It contains multiple jobs (like testing the backend or building docs) configured to run on an `ubuntu-latest` virtual machine (GitHub-hosted runner).
* **What it does:** The pipeline completely automates their CI process. It checks out the code, installs Python dependencies using tools like `uv`, lints the code formatting (often with `black` or `ruff`), and executes the test suite using `pytest` to ensure no new commits break the framework before they can be merged.
